# Payment and question-access integration — staged, not ready to deploy

This directory and `../payment-integration/` contain an **incomplete, disabled candidate**. Do not upload or deploy them, change the live Paddle catalog, enable feature flags, connect notification destinations, remove public question read, or take real payments based on this work. The live dashboard and Appwrite configuration are unchanged.

## What is implemented and locally tested

- **Checkout:** `src/checkout.mjs`, `checkout-session.cjs`, `checkout-binding.cjs`, `price-policy.cjs` and `catalog-config.cjs` authenticate an Appwrite JWT, bind the verified user and explicit renewal choice, and verify the chosen price via Paddle's server API. A **one-time price** is required for the default no-renewal choice; a recurring price is used only when selected explicitly. Missing, duplicate, incorrect, inactive, mispriced or incorrectly recurring IDs fail closed. No live prices were created or modified. Three new one-time IDs, matching $15/$36/$99, are still required; existing recurring prices must remain intact. Verify restrictions and compatibility of each existing founding discount against those new prices.
- **Webhook and mapping:** `src/main.mjs`, `paddle-webhook.cjs`, `appwrite-event-store.cjs`, `src/worker.mjs`, `process-queue.cjs`, `process-event.cjs`, `appwrite-queue-store.cjs` and `appwrite-mapping-store.cjs` stage signed notifications in a private, idempotent queue, read current Paddle records, verify the signed account/price binding, and create an immutable private mapping for either a recurring subscription or a one-time transaction. They **do not cancel live subscriptions**. Failed records remain pending; unsupported cases go to manual review. The webhook and worker are disabled by default.
- **Access:** `src/access.mjs`, `entitlement-service.cjs`, `entitlement-policy.cjs`, `one-time-policy.cjs` and `paddle-client.cjs` check Paddle data server-side, including complete adjustment pagination. One-time access is calculated from captured payment time as 30/90/365 days; recurring access requires the active opted-in subscription. Approved refunds, credits and chargebacks conservatively require manual review, including partial or older adjustments. Zero-cost transactions without a captured payment also require review. These policies require product-owner review and real testing.
- **Question delivery:** `src/questions.mjs`, `question-access.cjs`, `question-routes.cjs`, `appwrite-questions.cjs` and `appwrite-usage-store.cjs` stage authenticated question delivery, private per-user quotas, metadata-only catalogue responses, and a separate authorized-review path. A server-owned migration marker and cutoff block older accounts until migrated. The actual question and usage tables, indexes, function and permissions have not been configured. The gateway remains disabled by default.
- **Dashboard candidate:** `../payment-integration/dashboard.html` is generated from main commit `2d8d0d0` by `build-staged-dashboard.py`, imports the candidate adapters, and defaults to **fail closed**, not the insecure legacy path. It stages authenticated access, block hydration, server-managed trial state, a nonrenewing-by-default checkbox and legacy-history hydration. It is **not the live dashboard**. The static guard confirms the protected exam markup (`#screen-block`, `#endModal`, `#issueModal`, `#labPopup`) and every stylesheet remain unchanged. A mocked Chromium smoke test exercises boot, blocks, trial, checkout choices and migration guards, not real integrations.
- **Legacy history:** `legacy-history.cjs`/`.mjs` preserve unverified aggregate history for display. `legacy-migration.cjs` builds a one-time private migration plan from a trusted pre-cutover snapshot, preserves eligible referenced question IDs, bounds trial state and never trusts legacy paid preferences. The writer does not overwrite an existing usage record. **No bulk snapshot, cutoff enforcement in the legacy site, or migration operation has run.** Existing client-editable preferences can be forged: grandfathering them into review access is a product/security decision requiring Ali's approval. The bank was publicly readable before cutover, but malicious users could claim current IDs in those preferences. Preserve history without silently opening future bank items; plan a maintenance/freeze and a fixed allowed-ID snapshot so progress is not lost while migration runs.

## Important behavior differences and unfinished work

1. The staged quota charges each newly **delivered distinct question**, not each first answer as the old dashboard does; an opened but unanswered item consumes allowance. Previously delivered questions can be reviewed without another charge. The old and candidate daily boundaries are UTC, but the candidate uses the server clock. Past questions delivered during paid access are not automatically available for free review after expiry. These are material user-facing differences requiring approval, copy review and real testing—not silently deployable behavior.
2. The current live dashboard still downloads the whole bank, trusts client-editable subscription preferences and opens recurring checkout directly. The live questions table remains publicly readable. The staged dashboard is based on pinned main commit `2d8d0d0`; before a future release, compare current main and rebase the changes without overwriting unapproved branding. Do not change the protected exam surface.
3. Actual Appwrite transaction isolation/conflict detection, schema and indexes, payload sizes, SDK/runtime compatibility, user-migration cutoff, free-plan operation costs, performance and importer permission behavior have **not** been verified. The proposed private usage state uses a mediumtext/longtext `stateJson` field; require a properly sized private table and real concurrency tests. Keep the importer admin explicitly authorized, including read, when public read is eventually removed. The queue rejects payloads over 32 KB; assess real Paddle payload size before use.
4. There is no deployed migration runner, immutable bank-ID snapshot, cutover freeze, reconciliation/monitoring for missing events, review queue tooling, customer renewal-choice management, refund workflow, or operational recovery plan. A missing `transaction.completed` event means a paid user may not receive access until reconciliation/replay; 100% discounts with no captured payment require review. `checkout.html` has not been tested with real transaction or payment-method-update links. Promo restrictions and tax disclosure need verification.
5. The three new one-time prices and all function IDs are currently absent. Do not silently edit/archive/recreate existing prices or discounts. Code and tested integration first; only make additive catalog changes after Ali's approval and verify site-price/discount mapping.
6. Run full authenticated, concurrent, repeat/out-of-order, refund/cancel, purchase/expiry, free/trial, importer and real Paddle sandbox tests; verify accessibility and the exam interface. Then plan a carefully authorized live test. Ali must configure Appwrite/Paddle and enter secrets privately; this agent cannot access those accounts. Never ask for secret values in chat or commit them.

## Local tests

Install the pinned Node SDK: `npm ci --prefix payment-backend --ignore-scripts`; run `node --test tests/*.test.cjs`. `python3 tests/staged-dashboard-guard.py` compares the staged exam surface and styles with the pinned main revision. The optional `tests/staged-dashboard-smoke.mjs` requires `puppeteer-core`, `@sparticuz/chromium` and Chromium's shared libraries; it runs a local ephemeral server and mocks all Appwrite and Paddle requests. No mocks prove real production readiness.
