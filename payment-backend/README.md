# Payment and question-access integration — staged, not ready to deploy

This directory and `../payment-integration/` contain an **incomplete, disabled candidate**. Do not upload or deploy them, change the live Paddle catalog, enable feature flags, connect notification destinations, remove public question read, or take real payments based on this work. The live dashboard and Appwrite configuration are unchanged.

## What is implemented and locally tested

- **Checkout:** `src/checkout.mjs`, `checkout-session.cjs`, `checkout-binding.cjs`, `price-policy.cjs` and `catalog-config.cjs` authenticate an Appwrite JWT, bind the verified user and explicit renewal choice, and verify the chosen price via Paddle's server API. A **one-time price** is required for the default no-renewal choice; a recurring price is used only when selected explicitly. Missing, duplicate, incorrect, inactive, mispriced or incorrectly recurring IDs fail closed. No live prices were created or modified. Three new one-time IDs, matching $15/$36/$99, are still required; existing recurring prices must remain intact. Verify restrictions and compatibility of each existing founding discount against those new prices.
- **Webhook and mapping:** `src/main.mjs`, `paddle-webhook.cjs`, `appwrite-event-store.cjs`, `src/worker.mjs`, `process-queue.cjs`, `process-event.cjs`, `appwrite-queue-store.cjs` and `appwrite-mapping-store.cjs` stage signed notifications in a private, idempotent queue, read current Paddle records, verify the signed account/price binding, and create an immutable private mapping for either a recurring subscription or a one-time transaction. They **do not cancel live subscriptions**. Failed records remain pending; unsupported cases go to manual review. The webhook and worker are disabled by default.
- **Access:** `src/access.mjs`, `entitlement-service.cjs`, `entitlement-policy.cjs`, `one-time-policy.cjs` and `paddle-client.cjs` check Paddle data server-side, including complete adjustment pagination. One-time access is calculated from captured payment time as 30/90/365 days; recurring access requires the active opted-in subscription. Approved refunds, credits and chargebacks enter a proposed, version-bound manual review. Pending partial refunds/credits retain access by default; full refunds/credits and any chargeback restrict that billing source by default. A verified admin can explicitly allow or restrict that source after checking Paddle; independently free-granted questions and other valid paid sources are not revoked. Legacy-grandfathered IDs have no verifiable funding source. Zero-cost transactions without a captured payment require separate review. Ali accepted these proposed defaults (“okay if you think this is the best thing to do”); they still require real provider and operational testing.
- **Question delivery:** `src/questions.mjs`, `question-access.cjs`, `question-routes.cjs`, `appwrite-questions.cjs` and `appwrite-usage-store.cjs` stage authenticated question delivery, private per-user quotas, metadata-only catalogue responses, and a separate authorized-review path. A server-owned migration marker and cutoff block older accounts until migrated. The actual question and usage tables, indexes, function and permissions have not been configured. The gateway remains disabled by default.
- **Dashboard candidate:** `../payment-integration/dashboard.html` is generated from main commit `2d8d0d0` by `build-staged-dashboard.py`, imports the candidate adapters, and defaults to **fail closed**, not the insecure legacy path. It stages authenticated access, one-question-at-a-time hydration, server-managed trial state, a nonrenewing-by-default checkbox and legacy-history hydration. Navigation pauses the timer while a new question loads and restores the prior question on failure. It is **not the live dashboard**. The static guard confirms the protected exam markup (`#screen-block`, `#endModal`, `#issueModal`, `#labPopup`) and every stylesheet remain unchanged. A mocked Chromium smoke test exercises boot, blocks, trial, checkout choices and migration guards, not real integrations.
- **Refund review and catalog check:** `adjustment-policy.cjs`, `resolve-adjustments.cjs`, `refund-review-store.cjs`, `refund-admin.cjs` and `src/refund-admin.mjs` stage a private, server-authorized review queue with version-bound decisions and an append-only decision history. The exact Appwrite admin user ID is checked via a verified JWT; browser-supplied identities are ignored. A decision changes our access policy only—it never issues or reverses a Paddle refund. For recurring purchases it affects that subscription as a whole, not just an individual billing period. `../payment-integration/refund-reviews.html` is an unlinked, disabled candidate admin interface. `catalog-preflight.cjs`/`src/catalog-preflight.mjs` stage an admin-only, read-only comparison of six price IDs and three discount restrictions; passing the price check does not certify checkout or launch readiness. The review table, indexes, admin account, APIs and UI remain unconfigured and untested against real services. Ali accepted the proposed refund defaults, subject to real-world validation.
- **Legacy history:** `legacy-history.cjs`/`.mjs` preserve unverified aggregate history for display. `legacy-migration.cjs` builds a one-time private migration plan from a trusted pre-cutover snapshot, preserves eligible referenced question IDs, bounds trial state and never trusts legacy paid preferences. The writer does not overwrite an existing usage record. `legacy-snapshot-store.cjs`, `legacy-migration-runner.cjs`, `appwrite-legacy-users.cjs`, `appwrite-migration-review.cjs`, `src/legacy-snapshot.mjs` and `src/legacy-migrate.mjs` now stage an operator-only immutable bank snapshot, bounded resumable user migration, private review queue and cutoff checkpoint. They require explicit maintenance and grandfathering approval and remain disabled. **No real snapshot, cutoff enforcement in the legacy site, or migration operation has run.** Existing client-editable preferences can be forged: grandfathering them into review access is a product/security decision requiring Ali's approval. The bank was publicly readable before cutover, but malicious users could claim current IDs in those preferences. Preserve history without silently opening future bank items; plan a maintenance/freeze and a fixed allowed-ID snapshot so progress is not lost while migration runs.

### Staged recovery and health checks

- `src/reconcile.mjs`, `reconcile-events.cjs`, `appwrite-checkpoint-store.cjs` and `paddle-client.cjs` stage a read-only, authenticated Paddle Events API backfill into the private queue. The reconciler checks ordered pages, atomically checkpoints only after archival, deduplicates replays, and stops for an unapproved initial baseline or a possible 90-day retention gap. It is disabled by default. Paddle's Events API retains only 90 days; older transactions and subscriptions need a separately verified historical reconciliation before approving the initial baseline.
- `src/health.mjs` and `payment-health.cjs` stage an operator-only summary of pending events, manual-review and refund-review counts, and reconciliation age without logging customer data. **Console logs are not automatic alerts.** No real scheduler, notifications or end-to-end recovery were configured or tested. Both functions must have no client execute roles; header checks alone are not an authorization boundary.
- `src/legacy-snapshot.mjs` and `src/legacy-migrate.mjs` are separate scheduled operator functions with explicit enable, maintenance and grandfathering-approval flags. Snapshot and user migration run before the immutable cutoff and stop for unknown IDs, malformed history, capped trials or conflicting existing state. The private review queue records those cases. The site/importer must be genuinely frozen for a consistent snapshot; a boolean flag alone does not enforce a freeze, and Appwrite APIs may remain reachable. User-editable historical prefs can be forged, so this is an explicit business/security decision, not proof of prior use. The code has not been executed against real Appwrite.

## Important behavior differences and unfinished work

1. Ali delegated the free-quota choice and accepted the recommendation: the staged UI now requests one question when first displayed, rather than preloading/charging the entire block. A newly delivered, unanswered question consumes allowance; revisiting a previously delivered question does not. Paid-viewed questions are recorded in private usage state with their verified billing-source IDs for later review after expiry. A network response can be delivered/charged even if the browser closes before rendering; resuming that granted question should not charge again. The old and candidate daily boundaries are UTC, but the candidate uses the server clock. These differ from the old first-answer logic and require copy review and real testing. Granting past paid reviews is a student-friendly policy choice, not an industry-standard claim. The candidate now distinguishes free/legacy grants from paid grants and verifies each paid grant against its billing source. The proposed default keeps access during partial-refund review and restricts a paid source for a full refund/credit or chargeback; a server-verified admin may decide differently for that exact adjustment version. An independently free-granted question or a separate valid paid source remains reviewable. For recurring plans this is subscription-level, so an older full refund can restrict a later billing period until reviewed. Ali accepted the proposed default; it still requires real operational testing. Legacy-grandfathered IDs have no verifiable funding source and are not automatically revoked by a refund.
2. The current live dashboard still downloads the whole bank, trusts client-editable subscription preferences and opens recurring checkout directly. The live questions table remains publicly readable. The staged dashboard is based on pinned main commit `2d8d0d0`; before a future release, compare current main and rebase the changes without overwriting unapproved branding. Do not change the protected exam surface.
3. Actual Appwrite transaction isolation/conflict detection, schema and indexes, payload sizes, SDK/runtime compatibility, user-migration cutoff, free-plan operation costs, performance and importer permission behavior have **not** been verified. Usage state now requires a `paidGrants` field; any older staged records without it must fail closed and need a reviewed versioned migration. Subscription plan changes may invalidate the original price binding and require review. The staged outage fallback reports billing verification unavailable and permits only previously free/legacy-granted question reviews; it does not grant new questions, paid-only reviews, start a trial, spend free quota or open checkout while verification is down. Historical score summaries use saved legacy scores and item-level analysis is hidden when unavailable. This fallback has only mock tests; validate real Appwrite/Paddle outages and recovery before launch. The proposed private usage state uses a mediumtext/longtext `stateJson` field; require a properly sized private table and real concurrency tests. Keep the importer admin explicitly authorized, including read, when public read is eventually removed. The queue rejects payloads over 32 KB; assess real Paddle payload size before use.
4. The candidate migration runners, immutable bank-ID snapshot, Paddle-event reconciler, health checks and private review queue are not deployed or tested against real services. There is no enforced cutover freeze, automatic alerting, deployed/real-tested operator review interface, customer renewal-choice management, complete refund workflow, or validated operational recovery plan. A missing `transaction.completed` event means a paid user may not receive access until reconciliation/replay; 100% discounts with no captured payment require review. `checkout.html` has not been tested with real transaction or payment-method-update links. Promo restrictions and tax disclosure need verification.
5. The three new one-time prices and all function IDs are currently absent. Do not silently edit/archive/recreate existing prices or discounts. Code and tested integration first; only make additive catalog changes after Ali's approval and verify site-price/discount mapping.
6. Run full authenticated, concurrent, repeat/out-of-order, refund/cancel, purchase/expiry, free/trial, importer and real Paddle sandbox tests; verify accessibility and the exam interface. Then plan a carefully authorized live test. Ali must configure Appwrite/Paddle and enter secrets privately; this agent cannot access those accounts. Never ask for secret values in chat or commit them.
